# BMI270 acquisition path

Milestones 4.1 and 4.2 provide the flight-firmware path that initializes the
on-board BMI270 and publishes timestamped raw accelerometer/gyroscope samples.
The samples deliberately do not influence motor output yet.

## Dependency and ownership

The official Bosch BMI270 SensorAPI is pinned as the
`firmware/third_party/BMI270_SensorAPI` Git submodule at tag `v2.113.0`, commit
`41129fcfe39c583ee5462d79195741945d51c1fe`.

The boundaries are:

- `hardware/spi_device` defines the generic, injected SPI-device operations.
- `hardware/boards/flightcomputer_v1/board_imu` owns SPI3, GPIO routing, chip
  select, transfer timeout, and the microsecond delay implementation.
- `peripherals/bmi270/bmi270_driver` adapts that SPI device to the Bosch API,
  owns sensor configuration, and returns hardware-independent raw samples.
- `flight/sensors/imu_sample` owns hardware-independent body-axis mapping and
  freshness classification.
- `app/imu_service` owns periodic reads and the latest complete sample.
- `app/application_runtime` owns boot sequencing and configuration, while
  `app/imu_task` owns scheduled execution plus runtime fault, log, and debugger
  diagnostics. `app/application_tasks` only registers task definitions.

No peripheral module includes STM32 HAL types, and no application module
configures SPI registers or pins.

## V1 transport

Flight Computer V1 uses the tester-proven physical configuration:

| Function | V1 selection |
| --- | --- |
| SPI | SPI3, two-line master, mode 0, MSB first |
| SCK | PB3, AF6 |
| MISO | PB4, AF6 |
| MOSI | PB5, AF6 |
| Chip select | PD2, active low GPIO, high before output configuration |
| SPI clock | 42 MHz APB1 peripheral clock divided by 64 = 656.25 kHz |
| Transfer timeout | 20 ms |

The Bosch SPI read callback sets the register read bit and discards the dummy
byte received while the address is transmitted. Transfers and temporary
buffers are bounded, chip select is released after both successful and failed
transfers, and no runtime allocation is used.

## Sensor configuration

The range and filter settings retain the physically proven manufacturing
tester configuration. Milestone 4.2 raises both output data rates for the 1 kHz
flight service:

- accelerometer: 1.6 kHz, plus/minus 2 g, normal average-4 bandwidth,
  performance filter mode;
- gyroscope: 1.6 kHz, plus/minus 2000 degrees per second, normal bandwidth,
  power-optimized noise mode, performance filter mode.

Boot initializes and enables both sensors, then reads one raw six-axis sample.
After successful boot validation, a high-priority 1 kHz service reads one
sample per release. The sensor therefore produces data faster than the service
consumes it; the firmware reads the most recent register values rather than
trying to process every 1.6 kHz sensor update.

## Publication and body axes

The service builds a complete local sample before replacing its owned latest
snapshot. Each successful snapshot contains all six mapped raw values, a
microsecond acquisition-completion timestamp, a saturating 64-bit sequence,
and a validity flag. A failed read leaves the last good snapshot unchanged.

The provisional Flight Computer V1 convention is:

| Body axis | BMI270 sensor axis |
| --- | --- |
| Forward (+X) | +Y |
| Right (+Y) | +X |
| Down (+Z) | -Z |

This assumes the PCB top points toward the aircraft front and the component
side faces upward. The authoritative V1 PCB places the BMI270 package without
rotation, but the board has no explicit front-direction marker. Milestone 4.3
must therefore physically verify every acceleration and rotation sign before
the values can be used by control code.

Values remain raw sensor counts in Milestone 4.2. The mapped fields use signed
32-bit integers so negating the valid BMI270 value `-32768` is defined and
lossless.

## Freshness and failures

The configured freshness thresholds are:

- `FRESH`: sample age at most 2 ms;
- `STALE`: sample age greater than 2 ms and at most 10 ms;
- `LOST`: sample age greater than 10 ms, or the clock moved backward;
- `UNAVAILABLE`: no first sample has been published during the initial 10 ms
  startup allowance.

An individual SPI failure increments a saturating error counter but does not
discard the last good sample. Persistent failures transition the sample to
stale/lost, report the recoverable `FAULT_ID_IMU_COMMUNICATION`, and produce
transition-only logs. A later successful sample clears that communication
fault. Initialization or the initial boot read still reports the separate
`FAULT_ID_IMU_INITIALIZATION` and prevents registration of the service task.

Neither fault changes the current armed state by itself. The fail-closed IMU
gate belongs to Milestone 4.8, when motor control actually depends on IMU data.

## Scheduler load

The 1 kHz tasks are motor output, IMU acquisition, receiver service, and the
current open-loop flight-control step. USB service is 500 Hz. The placeholder
diagnostic tasks are 100 Hz, 10 Hz, and 1 Hz.

Every task already records its latest and maximum execution time. The 10 Hz
diagnostic task now sums the recorded maximum execution times of all enabled
1 kHz tasks and exposes both the conservative microsecond budget and permille
utilization. It logs once if that estimate reaches 70% of the 1 ms period.

## Request-driven inspection

Milestone 4.3a exposes the already-published service state through the bounded
USB `imu` command. The command copies the latest coherent mapped sample,
freshness and age, service counters, IMU task timing, and the current combined
1 kHz worst-case execution budget. It does not perform a second SPI read,
change acquisition cadence, publish a parallel diagnostic snapshot, or add a
scheduled task.

Use `./ofc device imu` for one snapshot or `./ofc device imu --watch` for the
tester-style live display. Watch mode is host-driven with a minimum 100 ms
polling interval. The command is rejected in `ARMED` and `FAILSAFE`, keeping
this potentially expensive formatting path out of active flight operation.

The firmware returns signed raw body-axis counts. The host alone converts the
configured ±2 g range using 16,384 counts/g and the ±2000 degree-per-second
range using 16.384 counts/(degree/second). Acceleration and rotation use
independent visual scales. These are configuration-derived diagnostic units;
stationary bias calibration is reported alongside the raw values. Once ready,
the response also contains the RAM-only bias and corrected gyro values.

## Startup gyro calibration

The existing 1 kHz IMU task feeds each distinct fresh sample to a separate,
hardware-independent calibration module; calibration never performs another
SPI read. Startup first waits for the configured 100 ms settling interval,
then requires both the configured 500 ms collection interval and at least 500
distinct samples. Any axis above 5 degrees per second restarts settling. At
the end of a candidate window, any axis above 0.5 degrees per second standard
deviation also restarts it.

For each axis, the module accumulates signed 64-bit `sum` and `sum_of_squares`.
The bias is the rounded arithmetic mean `sum / sample_count`; variance is
checked without a square root using `N * sum_of_squares - sum * sum`. The
accepted bias is frozen in RAM until reboot and corrected gyro values subtract
that bias from the mapped raw sample.

The lifecycle remains `INITIALIZING` and the RGB LED remains yellow until the
calibration is ready. A small startup coordinator then changes the LED to
green and performs the sole transition to `DISARMED`. Arm remains impossible
before that transition; the LED is synchronously turned off before arm
preparation. The result is not connected to motor control in this milestone.

## Deliberate milestone boundary

Milestone 4.3b does not implement BMI270 data-ready interrupts, filtering,
attitude estimation, or closed-loop control. Scheduled polling is sufficient
for the initial 1 kHz path; later
timing measurements can justify an interrupt-driven design if needed.
